# V3 initial student and operations setup

The migrated target keeps `gaurav`, `nikhil` and `devansh` as stable historical IDs. A missing joining date or meal eligibility date remains `null`; no date is inferred from a meal entry, an old Stay or this release. Historical Stays, rooms, fees, deposits, payments and balances are not imported into the operational target. The financial start date is unset until the owner approves a real future date during cutover.

Only a canonical Super Admin session may initialize students and operational settings. Use the existing `/admin/members` and related Super Admin workflows, which write student and account audit events. Keep a release journal entry with the actor, approved source of each fact, before/after value, time and API result; verify the corresponding application audit event. Use normal API/service flows, not direct MongoDB edits.

1. List all current and archived students. Confirm the three original IDs, names, historical calendar lookup and active/inactive status against an owner-signed roster. Set each current active state explicitly; archive only on evidence. Preserve IDs and historical meal references.
2. For each student, ask the owner for the exact meal eligibility start and, if applicable, end date. Record only documented dates. Leave unknown dates `null`, which blocks automatic meal participation. Confirm the new eligibility does not reclassify imported historical days as new dues. Test zero, one, three, four and many-student roster behavior.
3. Provision member login only when requested. Generate a unique account tied to one student, use a fresh protected secret, require password change, verify session revocation and role checks. Account access is independent of meal eligibility and Stay status. Confirm primary and recovery Super Admin accounts still work before and after provisioning.
4. Create **new** Hostel Stays only for occupants confirmed for the v3 period. Create fresh room definitions and capacity, then assignments for those Stays. A historical Stay or room number is context, not an operational carry-forward. A student may have meals without a Stay, room or login.
5. After the approved financial boundary is set, create new rent plans, due dates and optional deposit requirements with effective dates/months allowed by that boundary. Never issue a full-month room charge in a partly historical month. Do not create a receipt for an old deposit or carry forward an old credit. If an actual balance transfer is required, stop and obtain a separately designed, audited reconciliation procedure.
6. Run data, index and post-cutover finance verification. For each missing eligibility, room assignment, fee plan, deposit requirement or login decision, record `BLOCKED: <student ID>, <operation>, <missing evidence>` in the release journal. Do not infer a default from v2.

Student profile, eligibility, archive/reactivation and login changes must remain separately auditable. No operational billing is opened until required configuration and the owner-approved boundary are verified.
