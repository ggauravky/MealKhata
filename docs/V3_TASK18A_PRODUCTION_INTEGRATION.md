## Adapter design and exact identities

`backend/src/migrations/production/` opens no connection on import and exposes no application route. `createTask18ARehearsalController` is limited to `NODE_ENV=test` isolated rehearsal; the registry refuses construction in production mode. It binds the Task 17 staged controller to an independent identity observer, explicit step contracts, evidence verification, and protected checkpoint verification. No live operation handler ships. The local-only `migrate:v3` and restore CLI guards remain unchanged.

The trusted allowlist has four distinct database roles: v2 source, full recovery, fresh v3 target, and release-control journal. Each role binds exact Atlas project ID, cluster ID, database name, replica-set name, endpoint identity, credential principal, and privilege list. Independent Atlas control-plane, MongoDB handshake, and privilege observers must agree with that allowlist. Hostname substrings and caller-supplied observation objects are insufficient. The source principal has only `find`, `listCollections`, and `listIndexes`; any extra action fails. The journal's own connection observer must prove all seven control identity fields before Stage A, Stage B, or an action; matching its database name alone is insufficient. The control database must be distinct from source, recovery, and target. A future live adapter must authenticate its own control-plane response, journal connection, and handshake and receive separate code review. No such adapter exists yet.

The signed Stage A plan retains its three-field identity format for compatibility. The protected allowlist adds project, endpoint, principal, and privilege checks without changing signed lineage. Stage A fixes source/recovery/target identities, financial boundary decision, and procedure digest. The frozen archive is unknown when Stage A is created. After source writers stop, Stage B requires the final archive, sidecar, exact collection comparison, bounded meal delta, freeze attestation, and new owner/operator signatures bound to the original release ID. Earlier approvals cannot authorize Stage B.

## Action, approval, and checkpoint control

`RELEASE_STEP_CONTRACTS` lists every action from `read-source-inventory` through `open-writes`, plus approval-only `approve-frozen-amendment` and `rollback-connection`. Every contract states phase and predecessor, required owner/operator approval, evidence, permitted resources, allowed operations and write scope, checkpoint, verification, stop condition, and recovery procedure. The registry accepts only `disposable-mock` descriptors whose declared resources and operations exactly match the frozen contract. It passes only action, phase, and release ID to the mock runner, rejects approval-only handler substitution, unknown handlers, and extra checkpoint fields. Only a safe checkpoint ID and SHA-256 evidence digest enter the journal. A protected-evidence reader and resource-state observer must independently verify each checkpoint. No generic shell action, URI input, force flag, or verification bypass exists. JavaScript itself cannot confine an injected function's side effects; a future live adapter must enforce resource scope through isolated credentials and a reviewed process boundary before production activation.

Each action needs a separate, dual-signed approval valid for at most five minutes. Current signer authority is checked at execution. The Task 17 journal atomically consumes the nonce and records majority-journaled state transitions outside source and target. A changed plan, archive checksum, identity, signer authority, or handler result stops the release. Rollback requires its own fresh approval after `switch-connection`; it remains available after Stage B expiry, and any reserved/failed/completed rollback closes forward actions, including `open-writes`. Handler failure, failed journal update, crash after side effects, or restart with a reserved step is ambiguous: keep writes closed, preserve artifacts, and request manual review. Do not blindly retry or substitute a handler.

## Standalone read-only source authorization

The `read-source-inventory` approval is its own scope. Owner and a distinct operator sign the exact Stage A digest, action, expiry, and nonce. `verifyReadOnlyInventoryAuthorization` checks the action, current signer keys, five-minute expiry, observed principal against the protected expected principal, and exact read-only actions. It grants no archive, restore, migration, target-creation, or connection-switch authority. The nonce is consumed only by the durable journal when the staged action is reserved.

A future authorized operator must verify project, cluster, endpoint, replica set, database, principal, and privileges before opening a source connection. Read all collections and documents from one MongoDB replica-set snapshot transaction with `readConcern: snapshot`; compare collection names, indexes, and an independently observed write epoch before and after. A timed-out or changing source is preliminary, never frozen authority. Inventory all collection names, counts, index constraints, meal dates and revisions, original and additional participant IDs, prices and overrides, shares, snapshots and corrections, monthly rates, old financial collections, and exact student/household paise. Preserve unknown collections in the complete encrypted archive and flag them. If an independently verified consistent snapshot is unavailable, stop. Keep student-level financial details in protected artifacts; stdout shows only aggregate counts and fingerprints.

## Historical and financial acceptance

The original v2 archive and legacy sidecar remain immutable. A frozen archive may append valid correction chains; the amendment never replaces the base archive. Compare original documents, frozen authority, authorized appended correction authority, current target authority, every date/month, participant IDs, prices, shares, actors, revisions, and exact integer paise. A one-paisa mismatch blocks replay. If the final meal-domain delta exceeds 256 documents or 8 MiB, recapture a base archive and rebuild an empty target; do not split or raise the bound ad hoc. Legitimate non-meal v2 drift requires an exact base/final archive-bound owner/operator review and stays in v2/recovery, without importing old liabilities.

The fresh target excludes old payments, settlements, room assignments, Stays, Room Fees, deposits, expenses, reimbursements, credits, allocations, payment references, and accounts. New accounts, eligibility, accommodation, and finance require explicit inputs. Missing eligibility blocks new meal activation. The boundary is an owner decision, never inferred from a fixture. Rehearsal must verify full historical, partial boundary, and operational months. `auditV3OperationalFinances` reads linked ledgers in one snapshot transaction and checks exact paise conservation across concurrent payments, reimbursements, deposits, and credit allocations.

| Historical proof | Immutable base | Frozen source | Target after replay | Stop condition |
| --- | --- | --- | --- | --- |
| Meal dates, participant IDs, status and six-unit shares | Authenticated base archive and sidecar | Full final archive plus bounded delta | Every date and participant | Missing or changed original fact |
| Prices, overrides and monthly rates | Baseline costs and saved rate records | Exact revised rate and override facts | Same historical price authority | One-paisa difference |
| Revisions, actors, timestamps and corrections | Original audit chain | Authorized appended chain only | Same chain and current authority | Deleted, reordered or unaudited correction |
| Daily and monthly costs | Original student/household paise | Independently recomputed frozen paise | Exact student/household paise | Any mismatch, including one paise |
| Non-meal collections | Complete encrypted archive | Exact drift inventory and separate review | Not imported into fresh finance | Unexplained drift or inherited old liability |

For financial reconciliation, first verify the owner-approved boundary and write-free or snapshot-consistent target state. Read payments, Room Fees, expenses, reimbursements, Stays, deposits, credits, allocations, and external-reference claims from one logical MongoDB snapshot. Check every effective date against the boundary, link each payment to its exact obligation, conserve integer paise for shared expenses and reclassifications, compare deposit receipts/refunds/deductions to held balances, and verify funded credit allocations and unique external references. Treat an invalid or incomplete snapshot as a stop condition. Keep detailed student-level findings in restricted evidence, not stdout.

## Recovery and rollback

Before a future switch, verify the complete encrypted v2 archive, separate recovery database, unchanged source, and previous application configuration. After an isolated switch, register every v3-only meal, correction, payment, reimbursement, Room Fee, Stay, deposit, credit, account, and student write with actor, time, paise, and external reference in restricted evidence. On failure, stop v3 writers and jobs, preserve both databases, obtain separate rollback approval, and restore the prior protected connection and release. Keep v2 writers closed pending another owner approval. Never copy v3 transactions into v2 automatically. Reconcile each external bank/processor reference manually against both ledgers before a new audited v2 entry or refund; freeze disputed references to prevent duplicate handling.

The offline rollback register compares complete target inventories taken at the write-open and write-stop checkpoints. It records added, changed, and removed document IDs and checksums plus allowlisted reconciliation fields; it omits account hashes and flags duplicated external references. Both inventories must come from independently verified consistent snapshots or a verified write-free state in a future production procedure. The isolated migration rehearsal records post-switch meals, payments, Room Fee charges/payments, an expense and reimbursement; it runs the financial audit, builds the restricted write register, restores the original connection, and verifies unchanged v2 source collection checksums. The browser fixture separately exercises those domains and the financial overview through real APIs. Automated rollback currently re-observes source, recovery, and target identities; loss of target connectivity blocks it. A separately reviewed emergency rollback path must prove source/control identities, preserve target outage evidence, and obtain new owner/operator authorization before any live use. No identity check is silently skipped in Task 18A.
